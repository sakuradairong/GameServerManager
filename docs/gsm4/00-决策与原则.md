# GSM4 决策与原则

## 1. 产品定位

| 项目 | 说明 |
|------|------|
| 产品名 | GameServerManager 4（简称 **GSM4**） |
| 前代 | GSM3（本仓库 `main`） |
| 形态 | Web 管理面板：主机监控、终端、实例、游戏部署、文件、环境、插件等 |
| 部署场景 | Windows x64 / Linux x64 / Linux ARM64；Docker 多架构；单机 `data/` 卷 |

GSM4 不是「把 GSM3 文件拆一拆」，而是 **同一产品能力的下一代实现**：保留用户心智与可迁移状态，重做模块边界与部署内核。

## 2. 分支策略（已定）

```text
main              GSM3 稳定线（热修、既有发版）
gsm4/main         GSM4 主线（orphan，空根起步，无 GSM3 提交历史）
cursor/gsm4-*     单次里程碑工作分支 → PR 合入 gsm4/main
```

### 规则

1. **不在 `main` 上删除或替换 GSM3 源码树来「变成 GSM4」。**
2. `gsm4/main` 使用 `git checkout --orphan gsm4/main` 创建，首提交仅为 GSM4 工程与本文档副本（或文档仍留在 `main` 的 `docs/gsm4/`，实现代码只在 orphan 线）。
3. `gsm4/main` **不预期 merge 回 `main`**（历史无关）。发布方式：
   - 过渡期：并行维护两个默认发布通道（GSM3 release / GSM4 release）
   - 成熟后：可将默认分支切到 `gsm4/main`，`main` 冻结为 `gsm3/main` 或打 `gsm3-final` tag
4. 方案文档先合入 `main` 的 `docs/gsm4/`，便于在现有评审流程中讨论；实现代码只进 `gsm4/main`。

### 为何选 orphan 而不是「从 main 拉分支再清空」

- 避免 10 万行遗产 diff 污染每个 PR  
- 强迫按新模块边界生长，降低「剪贴旧上帝文件」诱惑  
- 对照旧实现用 `git show main:path` 即可，不必同树共存

## 3. 技术选型（已定）

| 层 | 选择 | 理由 |
|----|------|------|
| Runtime | Node.js 20 LTS | PTY / SteamCMD / 本机 FS 亲和；团队栈连续 |
| 包管理 | npm workspaces（或后续评估 pnpm） | 与现有习惯接近，降低迁移税 |
| Server | Fastify + Zod | schema 优先、插件化；比 Express 更利薄路由 |
| Realtime | Socket.IO | 终端与长任务进度已验证；首版不自研协议 |
| Client | React + Vite + TypeScript | SPA 面板合适 |
| UI | 延续面板自有风格（Tailwind 等）；**新页面不用 Ant Design** | 与 GSM3 AGENTS 约束一致 |
| 状态 | 轻量客户端 store + 单一 ApiClient | 禁止页面内无约束状态爆炸 |
| 持久化 | `data/` 文件（JSON/目录） | 契合 Docker 卷与单机面板；首版不上 DB |
| 共享 | `packages/shared`（Zod schema / 事件名 / DTO） | 前后端契约同仓，消灭路径不一致类 bug |
| 迁移 | `packages/migrator` | GSM3 `data/` → GSM4 `data/` |

### 明确不做（首版非目标）

- 换语言（Go / Rust）整写服务端  
- 上微服务 / 强上 PostgreSQL  
- Electron 桌面壳  
- 为重写而大升级到不兼容的 UI 框架  
- API 与 GSM3 逐路由兼容层（成本高、会锁死坏设计）

## 4. 兼容与迁移策略（已定）

| 维度 | 策略 |
|------|------|
| HTTP API | 新前缀 `/api/v1`，**不保证**与 GSM3 路径一致 |
| 实时事件 | 新命名空间（如 `deploy:*`），不沿用多套前缀并行 |
| 磁盘游戏服 | **不移动**；只迁移面板侧指针与元数据 |
| 面板数据 | 一次性迁移工具（见 [02-数据与迁移](./02-数据与迁移.md)） |
| Token 键 | GSM4 使用 `gsm4_token`；迁移期客户端可双读 `gsm3_token` |
| 外部 API | 语义对齐「API Key 控制实例」，路径可重新设计并出迁移说明 |

## 5. 设计原则

1. **实例是唯一运行时真相**：部署成功 = 提交/更新 Instance；失败可回滚新建实例。  
2. **部署只有一条内核**：游戏差异进 Executor，不进路由拷贝。  
3. **路由极薄**：认证、Zod 校验、调用 application service；无业务长流程。  
4. **进度可取消**：所有长任务进 Session，取消语义一致。  
5. **路径安全默认开启**：默认安装在 `defaultInstallPath` 沙箱下；自定义绝对路径需显式高级选项。  
6. **解压必经安全过滤器**：tar/zip/7z 统一适配层，禁止裸 `sh -c` 拼路径成为主路径。  
7. **平台能力用能力表声明**：ARM 不支持 SteamCMD 等在 Executor 元数据声明，UI 按能力隐藏。  
8. **每个里程碑可运行**：宁可少功能，不交半截上帝文件。  
9. **文档先行**：域边界或事件契约变更先改 `docs/gsm4/`。

## 6. 与 GSM3 仓库约束的关系

GSM3 的 `AGENTS.md` 仍约束 `main` 上的改动。GSM4 将在 orphan 线提供自己的 `AGENTS.md`，继承合理条款（如 `data/` 目录、认证中间件、弹窗动画、消息组件、多路径尝试、禁止随意上 Ant Design 新页等），删除仅适用于遗产结构的条款。
